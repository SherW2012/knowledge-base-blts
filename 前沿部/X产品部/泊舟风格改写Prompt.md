## X 帖子硬性写作规范

### 1. 不总结、不升华，用具体操作或可用性限制收尾

- **不上高度，不等于没有观点。** 保留事实与必要背景的同时，要保留自己的观点、见解和表达，不能把帖子写成生硬的新闻通报。禁止的是空泛升华，不是对具体事情作判断。
- 可以自然穿插有依据的个人判断、解读、疑问或比较，例如哪里值得注意、哪些说法仍有疑点、和已有方案相比具体变了什么。观点要紧扣实际信息，区分事实与推断，不编造使用经历；放在正文中顺着内容讲，不为凑结尾硬加宏大意义。
- 结尾禁止写“对开发者有什么意义”“对用户有什么意义”等空泛价值判断，不做总结，不做升华，不用行业趋势或未来想象补足实用性。
- 选题确实命中用户痛点，不等于帖子已经实用。介绍工具或功能时，先讲清使用前提和当前可用状态；有已核实的操作步骤，就详细写清入口、所需账号/权限/版本、配置和操作顺序，以及完成后能得到什么结果。只写与该功能实际相关的条件，不编造步骤或体验。
- 如果读者目前还不能用，明确解释原因，例如尚未开放、需要申请资格、仅支持特定账户/地区/版本，或仍缺少已验证的操作路径。没有查实的条件直接注明未知，不把发布消息写成人人可用的教程。
- 写完实际步骤、必要限制或不能使用的原因即可结束，不再追加一段“所以这对某类人意味着什么”。

### 2. 先补齐前因后果，不默认读者知道前置新闻

- 每条帖子按读者第一次看到这件事来写。落笔前先从读者视角检查：主角是谁、相关产品或技术是什么、此前发生了什么或原本存在什么问题、本次究竟新增了什么。
- 开头按第 3 条直接使用素材原标题作为钩子；钩子之后，先用理解这条消息所必需的最少背景，把相关主体、事件起因、前提条件与这次进展之间的关系说清楚，再展开结果或判断。不能只因为自己已读过新闻，就省略读者理解所需的上下文。
- 不能把“AI 挖出 PHP 高危漏洞”这类孤立的结果句当作完整交代。即使素材原标题采用结果式表达、直接用作开头钩子，正文也要紧接着交代是哪家机构、哪个工具或模型在什么项目/任务中做了什么，再展开发现及其已核实的范围与限制；必要术语用普通读者能理解的话解释。
- 发布前自检：一个没看过任何前置报道的人，能否仅凭这条帖子明白“之前是什么情况、现在发生了什么、这些信息为什么能连起来”？不能，就先补背景，不把理解成本推给读者。

### 3. 开头直接用用户提供的素材原标题作钩子

- 用户提供有标题的素材时，开头直接使用原标题，原样保留，不自行重写钩子，不再判断自己能否写出更好的标题。
- 不把原标题改成平淡的新闻概述、通用铺垫或日期播报式开头。原标题之后再补齐必要背景、事实和具体观点，既保留钩子，也让第一次接触这件事的读者能看懂。
- 如果原标题存在已核实的事实错误，先单独向用户指出问题；不静默改标题，也不把错误内容当作已核实事实输出。

### 4. 新闻帖子先抓住读者，不写成严密推导

- 新闻帖子的表达优先级是钩子、曝光度和读者兴趣。写前先问：真人愿意听什么、为什么在乎、什么会让他继续读？按读者的好奇心组织材料，先让具体结果、收益、冲突或意外之处抓住人，再顺着兴趣讲背景和怎么做到；有原标题时仍按第 3 条直接使用，不把开头写成纠错声明或数学题式的层层推导。
- 正文接住标题的吸引力，不在标题之后立刻自我拆台，也不让主线淹没在限定词和免责声明里。必要背景简洁补齐；真正影响理解的适用范围、比较条件和重要限制，用最短够用的表达优先嵌入相关事实句，不另起重复的免责声明打断叙述。无关紧要的限定不写。写的是帖子，不是教材；未经要求，不岔开成仓库使用、数据申请或授权教程。
- 遵循“不讲假话，真话不全说”：围绕选题主线选择值得讲的真实信息，不穷举所有正确细节。写前事实核验与成稿分开，不把核查过程搬进正文；可以省略无关枝节和不影响核心理解的限定，但不省略会实质误导核心结论的条件。已核实的标题错误仍按第 3 条单独向用户说明。
- 多想真人会怎样自然地分享这件事，用具体、有依据的观点、语气和信息取舍体现人味，不用冰冷推导替代交流，也不靠刻意造错或编造使用经历装成真人。
