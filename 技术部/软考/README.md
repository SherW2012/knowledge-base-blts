# 软考知识库

本知识库按计算机学科主题组织，以Markdown文档承载，便于全文检索、持续补充、版本管理和网页浏览。

## 内容原则

- 知识条目按主题组织成系统性的说明文档，不使用零散问答或聊天记录结构。
- 图只用于解释单靠文字不容易看清的关系、流程、层次或状态，不为满足数量而重复画图。
- 空间结构、物理包含、复杂分层和多角色协作优先采用定制SVG；严格时序、状态迁移和简单步骤流程优先采用Mermaid。
- 图必须通过分组、位置、颜色、简短职责和必要连线承担解释任务，不能把“存在一张图”等同于“已经解释清楚”。
- 区分标准明确规定的事实、工程实现和帮助理解的解释。
- 涉及标准或规范时，以标准文本和明确采用的教材术语为准。
- 不为了维护既有结论而反向编造理由。
- 缩写存在歧义时明确标注，不擅自替换。
- 使用直接、具体的技术解释，不采用比喻替代定义。
- 详略得当：基础、常用、高频的知识点必须充分展开讲透，只有次要或边缘的内容才从简。"不重要"意味着可以写短，"重要"就必须写透，不能一刀切地都写得克制。
- 讲到读者能自洽理解为止：每个关键知识点按"定义 → 为什么/机制 → 边界或例子"三步走完再停，不在最该解释机制的地方戛然而止，也不在此处用"详见 X"打发读者。
- 知识点之间要有因果与衔接：后一个知识点要交代它为何承接前一个（承接、递进、对比、因果），让读者能顺着一条逻辑线读下去，而不是面对一组互不相干、生硬跳转的并列条目。

## 写作与维护规则

### 1. 内容范围

- 知识库首先服务于软考知识的**理解**、复习和概念辨析。"不写成覆盖全部工程实践的技术专著"限制的是**广度**（不追全部边角场景），不是**深度**——该讲清楚的核心知识点必须讲到位。
- 核心定义、原理、常见关系、易混概念和必要计算过程必须保留，并且要把其中的机制和"为什么"讲透，不能只列结论。
- 基础、常用、高频的知识点要充分展开；只有与主题相关但非核心、非高频的内容，才作简短延伸而不展开完整教程。判断标准是"这个点对理解和考试有多重要"，重要就展开，次要才从简。
- 用户追问暴露出的概念缺口应补齐讲透，但不把每一次追问都机械地扩写成独立大节。
- 专业英语章节只保存阅读方法、语法、固定搭配和词汇；题目涉及的架构、协议、算法等专业知识进入对应学科章节，两者通过链接关联，不混写。

### 2. 推荐结构

一篇普通主题文档通常按以下顺序组织：

1. 定义和定位；
2. 核心结构或工作过程；
3. 关键概念；
4. 容易混淆的概念对照；
5. 一个足以说明问题的案例或计算；
6. 核心结论与相关章节。

章节数量以内容逻辑为准。内容很短、只能说明一个局部概念的小节应与相邻章节合并，不能把每个术语机械地拆成一节。

**衔接连贯**是重点要求：相邻小节之间要有过渡，新小节开头点明它与上一节的关系（承接、递进、对比或因果），不要从一个概念直接跳到下一个而不交代联系。整篇读下来应是一条有逻辑的线，而非一叠彼此孤立的卡片。一个概念若是理解下一个概念的前提，就要在引出下一个时显式说明这层依赖。

### 3. 篇幅控制

| 主题规模 | 建议正文规模 | 适用情况 |
|---|---:|---|
| 简单概念 | 约800～1800字 | 单一定义、分类或区别 |
| 中等主题 | 约1800～3500字 | 包含一组相关概念和一条主要流程 |
| 复杂基础主题 | 约3500～6000字 | 需要解释多层结构、算法或完整工作过程 |

超过建议规模时，依次检查：

1. 是否重复用正文、表格、图和总结表达同一结论；
2. 是否把非核心工程细节写成了完整教程；
3. 是否存在可以合并的相邻小节；
4. 是否与其他文档重复，应改用交叉链接；
5. 是否确实包含两个能够独立学习的主题，需要拆分文档。

上表是参考区间，不是硬性上限。**篇幅服从理解需要**：核心、高频的知识点该长则长，务必把机制和因果讲透，必要时可以超出参考区间；次要内容才从简。要压缩的永远是重复表述和边缘内容，而不是牺牲核心知识点的完整解释。非关键内容不得因为格式对称而获得与核心内容同等的篇幅。

### 4. 图、表和案例

- 普通主题保留1至5幅真正必要的图；复杂流程可以适当增加。
- 同一关系已经由清晰表格表达时，不再绘制内容相同的图。
- 对照项较多时优先使用表格，步骤和状态变化优先使用流程图、时序图或状态图。
- 每篇最多保留一个主要案例；只有不同案例分别解释不同难点时才增加。
- 代码只保留能够解释核心概念的最小片段，不展开完整项目结构。

### 5. 去重与链接

- 一个概念选择一篇文档作为主要解释位置。其他文档在用到它时，仍要给出当前语境下**够用的解释**——至少让读者不点链接也能读懂本段的逻辑——再链接到主文档深入。链接是"想进一步了解"的补充，不能用一句"详见 X"代替本段必要的解释，尤其不能在正要解释核心机制处直接甩链接。
- DFD、内聚、TCP连接、HTTP、TLS等已有独立章节的内容，不在综合文章中再次完整展开。
- “核心结论”只压缩前文，不逐段复述。
- 新增内容前先检查现有章节，优先整合，不轻易建立内容重叠的新文档。

### 6. 修改与审查

- 补充内容后检查标题顺序、章节粒度、重复表述、交叉链接和图表渲染，并额外检查两点：核心知识点是否讲透了机制与"为什么"，相邻小节之间是否有因果衔接、有没有生硬跳转。
- 新内容导致文章明显超长时，应同时压缩旧内容或拆分主题，不能只在末尾持续追加；但压缩的对象是重复表述和次要内容，核心知识点的完整解释不因控制篇幅而被砍。
- 对设计模式这类由大量并列而又各自具有完整机制的知识体系，应提升为独立目录并拆分子章节；每个必要单元可以拥有自己的机制图，不受普通主题图数量建议限制。

### 7. 文件路径与导航顺序

- Markdown文件名是供链接长期引用的稳定路径，不因章节前后次序变化而重命名。
- 根目录及各知识目录使用`_nav.json`中的`order`数组控制网页展示顺序；调整顺序时只修改对应清单。
- 新建页面时使用该目录中尚未占用的编号作为稳定文件名，再把文件名插入`_nav.json`的目标位置。编号只用于辨认文件，不再承担实时排序职责。
- 浏览器对未写入清单的页面采用自然排序并追加显示，避免内容暂时不可见；校验程序会将这种情况报告为错误，提醒补齐清单。
- 删除或改名之前，使用`python web/validate_kb.py --references "相对路径.md"`查看反向引用；完成修改后运行`校验知识库.cmd`检查导航完整性、内部链接、图片引用和代码块闭合情况。
- 精简时不得删除核心定义、关键原理、常见考点、必要公式、关键边界和能够消除误解的解释。
- 知识库正文不记录做题过程、对话经过或答案公布规则。
