# 软件维护、逆向工程与遗留系统

## 1. 软件交付以后并没有结束

软件投入使用以后，仍会因为缺陷、环境变化、业务变化和质量改进持续修改。软件维护就是交付后的修改活动。

软考高频考法主要集中在：

- 四类软件维护；
- 逆向工程、重构、再工程的区别；
- 遗留系统怎样处置；
- 可维护性与维护成本。

## 2. 四类软件维护

### 2.1 改正性维护

发现软件中已有缺陷并修复。

```text
关键词：修Bug、纠错、修复错误结果
```

例如生产环境发现某报表计算错误，修改代码使结果恢复正确。

### 2.2 适应性维护

外部环境改变后，为了让软件继续正常运行而修改。

```text
关键词：环境变了，软件要适应
```

例如：

- 操作系统升级；
- 数据库版本更换；
- 法规或外部接口发生变化；
- 硬件平台变化。

### 2.3 完善性维护

用户提出新需求，或者为了改善性能、可用性等而扩展和改进软件。

```text
关键词：增加能力、改善体验、提高性能
```

例如在已有系统中增加批量导出功能。

### 2.4 预防性维护

当前未必已经出错，但为了降低未来故障和维护风险而提前改造。

例如：

- 重构复杂代码；
- 清理潜在缺陷；
- 替换即将停止支持的技术；
- 提升测试覆盖和可维护性。

## 3. 四类维护快速区分

```text
已经错了 → 改正性
环境变了 → 适应性
想更好/加功能 → 完善性
怕以后出问题，提前改 → 预防性
```

考试题常用场景描述而不是直接给术语，先找“为什么要改”通常就能判断。

## 4. 软件维护为什么昂贵

维护成本高的原因通常不只是“写代码慢”，而是维护者需要重新理解已有系统。

影响可维护性的因素包括：

- 代码和架构是否清晰；
- 文档是否准确；
- 模块耦合是否合理；
- 测试是否充分；
- 是否存在大量隐式规则；
- 原开发人员是否仍在；
- 技术是否已经过时。

因此高内聚、低耦合、清晰接口、自动化测试和准确文档都会降低长期维护成本。

## 5. 逆向工程

逆向工程从已有程序、代码、数据库或运行行为出发，恢复更高层次的信息。

```text
代码 / 数据 / 现有系统
        ↓
分析、抽取
        ↓
设计信息、结构、需求或业务规则
```

核心是：**从低层实现向高层理解。**

逆向工程本身不一定修改现有系统，它首先是“理解和恢复信息”。

## 6. 正向工程

正向工程是正常的软件开发方向：

```text
需求 → 设计 → 编码 → 系统
```

因此：

```text
正向工程：从抽象到实现
逆向工程：从实现恢复抽象
```

## 7. 重构

重构是在**不改变外部可观察行为**的前提下，调整内部结构，使代码更容易理解和维护。

例如：

- 拆分过长函数；
- 消除重复代码；
- 重命名含义不清的变量；
- 调整类职责。

重构与完善性维护可能在实际工程中同时出现，但考试定义上要抓住：**重构强调内部结构改善，不以增加新功能为目标。**

## 8. 再工程

软件再工程通常是对既有系统进行分析和改造，使其以更好的形式继续使用。

典型过程可以包括：

```text
现有系统
  ↓
逆向工程：理解现状
  ↓
重构 / 重设计 / 数据重构
  ↓
正向工程：重新实现或整理
  ↓
改进后的系统
```

所以：

- 逆向工程是再工程可能采用的一个阶段；
- 再工程比逆向工程范围更大；
- 再工程通常会产生经过改造的新系统或新版本。

## 9. 遗留系统

遗留系统不是简单指“旧软件”，而是仍在承担重要业务、却因技术、结构、文档或维护能力问题而越来越难演化的既有系统。

常见特征：

- 技术陈旧；
- 文档缺失；
- 代码结构复杂；
- 业务规则高度沉淀在系统中；
- 替换风险很高；
- 与大量外围系统存在耦合。

## 10. 遗留系统的处置策略

是否立即重写，要同时看**业务价值**和**系统质量**。

可以建立四象限：

| 业务价值 | 系统质量 | 典型策略 |
|---|---|---|
| 高 | 高 | 继续维护与演化 |
| 高 | 低 | 重点改造、再工程或逐步替换 |
| 低 | 高 | 评估保留价值，控制投入 |
| 低 | 低 | 考虑淘汰 |

“旧”本身不是淘汰理由。一个系统即使技术陈旧，只要承担关键业务且替换风险极高，也可能需要长期保留并逐步改造。

## 11. 迁移与替换

大型遗留系统一般不适合毫无过渡地整体重写。常见思路：

- 接口封装；
- 数据迁移；
- 模块逐步替换；
- 新旧系统并行一段时间；
- 通过服务接口把旧能力暴露给新系统。

这类题如果问“降低一次性替换风险”，通常要想到渐进式迁移，而不是直接全部推倒重来。

## 12. 常见概念对照

| 概念 | 是否修改系统 | 核心目的 |
|---|---:|---|
| 逆向工程 | 不一定 | 从现有实现恢复高层信息 |
| 重构 | 是 | 不改变外部行为，改善内部结构 |
| 再工程 | 是 | 系统性分析和改造旧系统 |
| 正向工程 | 是 | 从需求设计走向实现 |
| 软件维护 | 是 | 交付后修复、适应、完善或预防问题 |

## 13. 做题固定判断

```text
为什么修改？
├── 修已有错误 → 改正性维护
├── 外部环境变化 → 适应性维护
├── 新功能/体验/性能提升 → 完善性维护
└── 提前降低未来风险 → 预防性维护

从代码恢复设计 → 逆向工程
不改行为只整理内部结构 → 重构
理解旧系统并系统性改造 → 再工程
```

## 核心关系

```text
维护 = 软件交付后的持续修改

逆向工程：实现 → 抽象理解
正向工程：需求/设计 → 实现
再工程：理解旧系统 + 改造 + 重新形成更可维护的系统
```
